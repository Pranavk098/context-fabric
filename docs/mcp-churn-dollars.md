# E-2: MCP churn in dollars, after the expected first announcement

Generated by `scripts/mcp_churn_dollars.py`. Aggregates only: counts, tokens,
dollars and session ordinals; no paths, prompts, commands or transcript text.
Dollars are API list-price equivalents, not a bill.

## What was counted

- Sessions scanned in the window: 1,019; sessions with at least one `deferred_tools_delta` or `mcp_instructions_delta` attachment: 997.
- Attachment lines: 3,104. Of these, 1,590 are the expected first announcement of a kind in their session; 1,514 are repeats.
- The R-7 headline count of 3,104 attachments therefore overstates churn 2.1x by line count.
- Repeat attachments carry ~4,407,730 tokens (bytes / 4, the same estimate `cfxd waste` prints).

## Sessions flagged: old vs new rule

| rule | test per session | sessions |
|---|---|---|
| old (shipped `cfxd/waste.py`) | more than one of the same kind | 278 |
| new (first announcement excluded) | at least one repeat remains | 278 |
| naive: any attachment | at least one attachment | 997 |
| naive: more than one attachment in total | `deferred + instructions > 1` | 600 |

The shipped rule and the new rule flag the same sessions: it already requires a repeat, so excluding the first announcement does not change the session set. The inflation is in the attachment, token and dollar figures, not in which sessions are called churny. The two naive rows show the false-positive band a reader reaches if every announcement (or any two, including one of each kind) is treated as churn.

## Dollars under two cache bounds

| bound | price basis | dollars |
|---|---|---|
| lower | every repeat token as a cache **read** | $0.1512 |
| upper | every repeat token as a cache **write** (5-minute) | $2.6556 |

Priced sessions: 278; sessions with repeats but no known model: 0. Each session's repeats are priced at its dominant model family from the repo's `cfxd/data/prices.json`. The truth sits between the bounds: the same bytes are written once and then read on later turns, and neither bound charges the write once and the reads separately.

## Method

- Discovery, transcript streaming and attachment byte counting are imported from `cfxd/audit.py`; the repeat threshold (`_CHURN_MAX`) is imported from `cfxd/waste.py`. Neither module is modified.
- An attachment's size is the largest non-`type` field JSON-serialised once (`_attachment_bytes`), so the names list and the rendered text are not double counted. Tokens = bytes / 4.
- The expected first announcement is excluded per kind, matching the R-7 comment and code: one `deferred_tools_delta` and one `mcp_instructions_delta` per session are context; every later line is a repeat. Counting one first per session in total instead would leave 2,107 repeats in this window.
- Model family: the most common priced family among the session's assistant turns (`cfxd/routing.py`). Headless: the transcript's `entrypoint` field.

## Caveats

- One person's sessions on one machine; a 30-day window by file mtime. Counts, not a census.
- Attachment bytes measure the re-sent payload, not the marginal bill: prefix caching may turn most of a repeat into a cheap read, and the turn that receives it pays for the rest of its prompt too. The two bounds bracket the cache price only.
- Tokens are estimated from characters at 4 bytes/token, the same estimate `cfxd waste` reports; no tokenizer is run.
- A repeat is not always avoidable: a session that connects a new server or reloads instructions mid-run gets a legitimate second announcement. The sample exists so those can be checked by hand.
- A resumed session appends to the same transcript, so several invocation starts are counted as one session and only the first announcement per kind is excluded. That can understate churn, not overstate it.
